Question 1: From the given programs, can AFL be a sound analysis? Can it be complete?

AFL is neither sound nor complete, because it's a fuzzing tool that only reports crashes it actually observes during execution.
The results depends on the quality of the generated inputs, and it cannot guarantee to find all divide-by-zero errors in the programs.

Question 2: From the given programs, can CSA be a sound analysis? Can it be complete?

CSA is neither sound nor complete, because it's a static analyzer that uses abstract interpretation to explore the program paths.
 It can miss some divide-by-zero errors due to its path imprecision and conservative nature, and it can also report false positives when it cannot rule out certain paths.

Question 3: What are the pros and cons of using the CSA to find divide-by-zero errors?  Comment
on both the accuracy and cost of the analyzer under these two domains.

Accuracy:
- Pros: CSA is fully automatic and systematically explores the code statically, finding divide-by-zero that fuzzing misses before execution. And it does not require finding a crashing input.
- Cons: It is conservative and path-imprecise, yielding false positives that lower precision and can cause developer distrust. It also missed several real bugs. It is not fully sound because data/loop-dependent flows defeat its summaries.

Cost:
- Pros: No input generation or execution needed, so it does not run the target a huge number of times; it can analyze source that may not compile into a runnable binary and terminates without infinite fuzzing loops.
- Cons: It must build and model the whole program, which is time-consuming and scales poorly to large codebases; Loop invariants and complex arithmetic require expensive unrolling or must be abandoned.
